# AGENTS.md — Глоссарий, правила перевода и оформления PGN

## Структура проекта, компиляция и тестирование
- Все скомпилированные исполняемые файлы должны размещаться исключительно в директории `bin/` в корне проекта.
- При сборке всегда указывай явный путь вывода: `go build -o bin/<имя_утилиты> <путь_к_исходнику_или_пакету>`.
- Запрещено оставлять бинарники в директориях с исходным кодом (`src/`), в корне проекта или в любых других папках. Перед удалением переноси их в папку `bin/`
- Имя бинарного файла должно соответствовать имени исходного скрипта без расширения `.go`.
- Каждое изменение, добавление или исправление кода в Go-скриптах требует создания или обновления соответствующих unit-тестов.
- Тестовые файлы должны находиться строго в той же директории, что и изменяемый скрипт. Имя файла должно следовать стандартному соглашению Go: `<исходный_файл>_test.go`.
- Тесты должны покрывать основные сценарии использования, обработку некорректных входных данных, граничные случаи и проверку формата выходных данных.
- После внесения изменений обязательно запускай проверку: `go test ./src/...`. Фиксация изменений допускается только при статусе `PASS` всех тестов.
- Запрещено изменять сигнатуры экспортируемых функций без синхронного обновления тестов и всех мест вызова.
- Делай коммиты в git только после подтверждения
- Для сборки через Docker используй `make docker-build` (собирает образ и компилирует бинарники в `bin/`). Для разработки в контейнере используй `docker compose run dev bash` — открывает shell с Go-тулчейном и bind-монтированием всех директорий проекта.

## Конфигурация проекта и правила разработки
- Файлы `go.mod`, `go.sum` и `Dockerfile` находятся в корне проекта. Они являются централизованными конфигурационными файлами проекта и должны использоваться для всех этапов разработки, сборки и запуска.
- Управление зависимостями (`go mod tidy`, `go get`, `go mod download`) выполняй строго из корня проекта. Запрещено создавать дополнительные модули во вложенных папках или перемещать `go.mod`/`go.sum`.
- `go.sum` генерируется автоматически. Никогда не редактируй его вручную. При рассинхронизации зависимостей решай проблему через `go mod tidy`.
- `Dockerfile` в корне проекта описывает эталонное окружение для сборки и выполнения скриптов. При локальной отладке, запуске тестов или подготовке к деплою ориентируйся на его инструкции. Не дублируй шаги настройки среды в других файлах.
- Все файловые операции в коде (чтение PGN, запись Markdown, сохранение бинарников в `bin/`) должны корректно работать при запуске из корня проекта. Используй `os/exec`, `path/filepath` или относительные пути, отсчитываемые от корня.
- При добавлении внешних пакетов или изменении структуры проекта обязательно фиксируй обновления в `go.mod` и `go.sum`. Изменения в этих файлах должны сопровождаться тестами, проверяющими работоспособность скриптов в обновлённом окружении.

## Словарь технических маркеров PGN
> ⚙️ **Правило:** При встрече в оригинале заменяй маркеры на указанные аналоги. Вставляй их как inline-элементы сразу после хода или в конец комментария, разделяя пробелом.

### NAG (Numeric Annotation Glyphs)
| Код | Символ | Русский перевод | Пример в выводе |
|-----|--------|----------------|-----------------|
| `$1` | `±` | Небольшое преимущество белых | `12. Bg5±` |
| `$2` | `∓` | Небольшое преимущество чёрных | `12...Bg4∓` |
| `$3` | `+-` | Решающее преимущество белых | `15. Qh5+-` |
| `$4` | `-+` | Решающее преимущество чёрных | `15...Qh4-+` |
| `$5` | `+/=` | Лёгкое преимущество белых | `+/=` |
| `$6` | `=/+` | Лёгкое преимущество чёрных | `=/+` |
| `$10`| `=` | Равная позиция | `=` |
| `$13`| `∞` | Неясная позиция / Компенсация | `∞` |
| `$14`| `⩲` | Инициатива у белых | `⩲` |
| `$15`| `⩱` | Инициатива у чёрных | `⩱` |
| `$16`| `±` | Преимущество белых | `±` |
| `$17`| `∓` | Преимущество чёрных | `∓` |
| `$22`| `⨀` | Цугцванг | `⨀` |
| `$36`| `↑` | Инициатива / Напор | `↑` |
| `$40`| `→` | Атака | `→` |
| `$44`| `⇆` | Контригра | `⇆` |
| `$132`| `⌓` | Белые лучше развиты | `⌓` |
| `$133`| `⌓` | Чёрные лучше развиты | `⌓` |

> 💡 *Если в оригинале уже стоит стандартный символ (`±`, `∞` и т.д.), сохраняй его. Преобразовывай только `$N`-коды. Для неизвестных `$N` оставь код и добавь: `(NAG $N: не распознан)`.*

### Время, оценка и расширения (deprecated)
| Оригинал | Формат в оригинале | Преобразование в Markdown |
|-----------|-------------------|---------------------------|
| `%emt` | `%emt 0:04:21` | `Время на ход: 4 мин 21 сек` |
| `%clk` | `%clk 1:25:10` | `Оставшееся время: 1 ч 25 мин 10 сек` |
| `%eval` | `%eval +0.45` | `Оценка: +0.45` |
| `%eval` | `%eval #4` | `Мат в 4 хода` |
| `%M` | `%M12` | `Мат в 12 ходов` |
| `[%emt ...]` | `1. e4 [%emt 0:03:15]` | `1. e4 (3 мин 15 сек)` |
| `[%clk ...]` | `1... c5 [%clk 1:58:00]` | `1... c5 (1 ч 58 мин)` |
| `[%eval ...]` | `2. Nf3 [%eval +0.3]` | `2. Nf3 (+0.3)` |

### Результаты и статусы (deprecated)
| Оригинал | Русский эквивалент |
|-----------|-------------------|
| `1-0` | `1-0 (Победа белых)` |
| `0-1` | `0-1 (Победа чёрных)` |
| `1/2-1/2` | `1/2-1/2 (Ничья)` |
| `*` | `* (Игра продолжается / Результат не указан)` |

### Правила применения маркеров
1. **Позиционирование:** Вставляй преобразованный маркер сразу после хода или в конец inline-комментария.
2. **Комбинирование:** Если один ход содержит несколько маркеров, объединяй их через пробел: `12. Bg5 (+0.45) ±`
3. **Вложенность:** В вариантах `( ... )` и комментариях `{ ... }` маркеры сохраняются в том же формате.
4. **Числа и пробелы:** Не добавляй лишних переносов строк внутри ходов. Формат: `Ход → Маркер → Пробел → Следующий ход`.

## Правила обработки PGN

### 1. Сохранение нотации
- Ходы, варианты, вложенные скобки `( )`, `[ ]`, `{ }` и все шахматные символы **должны оставаться без изменений**.
- Пример: `1. e4 e5 2. Nf3 Nc6 3. Bb5 a6 {Хороший ход} 4. Ba4 Nf6` → переводится только текст в `{ }`, нотация не трогается.
- Если в оригинале есть анализ в квадратных скобках `[$variation ...]` или NAG-коды, сохраняй их как есть или аккуратно переноси в русскоязычные комментарии.

### 2. Оформление структуры глав и разделов
- Заголовок главы или партии оформляй строго как заголовок второго уровня: `## Chapter N: Название`.
- Подзаголовок, тему или подраздел размещай сразу под основным заголовком как заголовок третьего уровня: `### Название темы`.
- Запрещено дублировать названия глав или подзаголовков в таблицах, списках метаданных или отдельными блоками. Структура документа должна опираться исключительно на иерархию Markdown-заголовков.
- Пример корректного оформления заголовка:
  ```markdown
  ## Chapter 2: Распознавание слабых пешек

  ### Типы уязвимых пешек

  [Далее размещается нотация, комментарии и аналитический текст]

### 3. Последовательное оформление и запрет на вынос ходов
- Обрабатывай содержимое главы строго последовательно, сохраняя исходный порядок всех элементов.
- Запрещено создавать отдельные секции, блоки или списки с названиями "Ходы", "Нотация", "Партия" и аналогичными.
- Все ходы, варианты, фигурные и круглые скобки, а также текстовые комментарии должны оставаться ровно на тех местах, где они расположены в оригинале. Не накапливай, не пропускай и не переноси ходы в конец документа или в отдельные блоки.
- Если в исходном материале присутствует только текст — выводи только текст. Если только нотация — выводи только нотацию. Если они чередуются — сохраняй чередование.
- Комментарии к ходам размещай inline или с минимальным отступом сразу после соответствующего хода. Не выноси их в отдельные разделы в конце главы.
- Пример корректного оформления:
  ```text
  Введение или аналитический текст главы.
  1. e4 e5 2. Nf3 Nc6 {Комментарий к позиции}
  3. Bb5 a6 4. Ba4 Nf6
  Продолжение аналитического текста или разбор варианта.
  ```

### 4. Запрет на дублирование заголовков
- Подзаголовок третьего уровня (`###`) должен содержать **новую информацию** или указывать на конкретный подраздел. Запрещено дословно или почти дословно повторять текст заголовка второго уровня (`##`).
- Если весь раздел главы посвящён одной теме, указанной в `##`, подзаголовок `###` не добавляй. Сразу переходи к основному содержанию.
- Перед добавлением `###` проверяй: если после удаления из него префикса "Chapter N: " он совпадает с заголовком `##` более чем на 80% — такой подзаголовок запрещён.
- Примеры:

  ❌ **Неверно (дублирование):**
  ```markdown
  ## Chapter 19: Пример фиксированных пешек - французская защита

  ### Пример фиксированных пешек - французская защита
  ```

  ```markdown
  ## Chapter 20: Пешечные островки - введение

  ### Пешечные островки - введение
  ```

  ✅ **Верно (без дублирования, если подтемы нет):**
  ```markdown
  ## Chapter 20: Пешечные островки - введение

  [Сразу основной текст или нотация]
  ```

  ✅ **Верно (если подзаголовок уточняет конкретику):**
  ```markdown
  ## Chapter 20: Пешечные островки - введение

  ### Структурные последствия изоляции
  ```

### 5. Сохранение и позиционирование FEN
- Если в исходном материале главы указан FEN (расстановка фигур), обязательно сохрани его в выводе.
- Размещай FEN строго сразу после заголовка главы (`##`) или подзаголовка (`###`), перед основным текстом или нотацией.
- Формат вывода: строка начинается с `**FEN:**`, затем пробел и значение FEN в одинарных бэктиках.
- Пример корректного оформления:
  ```markdown
  ## Chapter 14: Изолированные сдвоенные пешки - введение

  **FEN:** `8/5p2/5p2/8/8/8/8/8 w - - 0 1`

  [Далее основной текст или нотация]
  ```

### 6. Форматирование шахматных ходов и комментариев
- **Парная запись ходов:** Записывай ходы белых и чёрных последовательно под одним номером. Формат: `N. ХодБелых ХодЧёрных`. Запрещено выносить ходы чёрных на отдельную строку или дублировать номер хода.
- **Сплошная запись без комментариев:** Если в последовательности ходов отсутствуют текстовые примечания, размещай все полуходы в одну непрерывную строку без переносов. Строго запрещено начинать каждый новый номер хода с новой строки, если к нему не привязан комментарий.
  ✅ Верно: `2. g3 e6 3. Bg2 d5 4. Nf3 dxc4 5. Qa4+ Nbd7 6. Qxc4 a6`
  ❌ Неверно: `2. g3 e6\n3. Bg2 d5\n4. Nf3 dxc4`
- **Перенос строк только с комментариями:** Разрыв строки допускается исключительно перед ходом, к которому относится комментарий. Отделяй блок ходов от блока комментария одной пустой строкой.
- **Удаление фигурных скобок:** Полностью удаляй символы `{` и `}` из итогового текста.
- **Размещение и отступы комментариев:** Выноси каждый комментарий на новую строку сразу после хода, к которому он относится. Перед текстом комментария добавляй отступ ровно в 2 пробела. Между номером хода и текстом комментария всегда ставь минимум один пробел.
- Пример корректного оформления:
  ```text
  2. g3 e6 3. Bg2 d5 4. Nf3 dxc4 5. Qa4+ Nbd7 6. Qxc4 a6 7. Qc2 c5 8. Nc3 Be7

    8...Be7 Как уже упоминалось в разделе теории, я думаю, это единственная попытка черных достичь играбельной позиции.

  9. O-O O-O 10. d4

    10. Rd1 Я предпочел такой порядок ходов, но выбор Непомнящего вполне приличный.

  ```

## Приоритеты и исключения
- Запрещено реорганизовывать структуру главы. Порядок следования элементов (текст -> ходы -> комментарии -> текст) должен быть сохранён без изменений. Любая группировка, накопление или перенос ходов считается ошибкой.
- Если в оригинале присутствует несколько FEN (например, для разных вариантов), размещай каждый непосредственно перед соответствующим фрагментом разбора.
- Не преобразовывай, не сокращай и не интерпретируй значение FEN. Копируй строку точно как в источнике.
- Если в исходнике есть тег `[FEN "..."]` в PGN-блоке, выноси его в формат выше только если он относится ко всей главе. Если FEN относится к конкретному ходу или варианту — оставляй его в контексте этого хода.

## Go-скрипты и инструменты

### `src/builders/fen_builder/fen_to_diagram.go`
- **Назначение:** Генерация изображения шахматной позиции из FEN-строки.
- **Параметры:** Строка FEN, путь для сохранения результата.
- **Требования:** Валидирует входную FEN. При некорректном формате возвращает ошибку, а не падает с panic.

### `src/builders/markdown_builder`
- **Назначение:** Конвертация PGN-файла в структурированный Markdown с применением всех правил из этого документа.
- **Параметры:** Имя входного PGN-файла, имя выходного Markdown-файла.
- **Требования:** Строго следует глоссарию, правилам форматирования ходов, комментариев и позиционирования FEN (разделы 1–7). Не добавляет стороннюю логику, не описанную в правилах.
- **Флаги:**
  - `--src` — путь к входному PGN-файлу (обязательный)
  - `--out` — путь к выходному Markdown-файлу (обязательный)
  - `--skip` — пропустить N глав с начала
  - `--chapters` — обработать только первые N глав
  - `--chapter-numbers` — список номеров глав через запятую (например, `1,3,5`)
  - `--inline-images` — заменить FEN на base64-изображения
  - `--numbered-lists` — форматировать нумерованные списки с отступом (по умолчанию: true)
  - `--dash-lists` — форматировать списки с тире с отступом (по умолчанию: false)
  - `--exam` — режим экзамена: обрабатывает только главы, где White или Black **полностью** равны указанной строке. Если глава содержит FEN — выводит только FEN без маркера `**FEN:**`. Если FEN отсутствует — применяется обычное форматирование.

### Служебные теги платформы Chessable
- `@@StartBracket@@` — заменяется на символ `(` в выходном файле
- `@@EndBracket@@` — заменяется на символ `)` в выходном файле
- Эти теги используются для группировки элементов (вариаций, аннотаций) в исходных PGN-файлах, экспортированных с платформы Chessable
- При добавлении новых тегов от Chessable следуй тому же принципу: простая замена тега на соответствующий символ без проверки содержимого между тегами

### Правила разработки и тестирования
- При любом изменении логики в `fen_builder` или `markdown_builder` обязательно создавай или обновляй соответствующие тесты.
- Тесты располагаются в той же директории: `src/builders/`. Имена файлов должны следовать соглашению Go: `<имя_скрипта>_test.go`.
- Тесты должны покрывать: успешные сценарии, обработку невалидных входных данных, граничные случаи и проверку соответствия выходного формата ожидаемой структуре.
- После внесения правок запускай проверку: `go test ./src/builders/...`. Коммит допускается только при успешном прохождении всех тестов.
